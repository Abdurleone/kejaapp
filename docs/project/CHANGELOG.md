- Backend POC.
- Auth, account management, property listings, property image management, saved properties, pricing, property inquiries, viewing requests, reviews, notifications, agency verification, admin moderation, movers, static web frontend, tests, seeding, and Insomnia collection.
- React Native (Expo) mobile app MVP for iOS and Android covering auth, discover/search, property detail, saved favorites, inquiries, and viewing requests — see `mobile/README.md`. Verified end-to-end on a real Android emulator, not just the Expo web preview.
- CI (GitHub Actions), Docker images for backend/frontend, docker-compose for local/staging, and health check endpoints — see `docs/devops.md`.
- ESLint across backend/frontend/mobile (each with its own flat config) wired into CI, Dependabot for weekly dependency updates, a Jest + React Native Testing Library test setup for mobile, and a fix for 11 moderate mobile dependency vulnerabilities.
- Seeded demo data expanded from 2 to 9 counties (11 available properties) with matching mover coverage, and a property detail page + inquiry/viewing-request forms added to the web frontend (previously mobile-only), closing the gap where the Discover page's "Details" button had no handler at all.
- Fixed the Discover/Saved property cards hiding the star-rating summary behind the description text (it was only ever shown when a property had no description, so it almost never rendered), and seeded 15 reviews across 9 properties (2 more tenant demo users added for reviewer variety) so ratings actually have real, non-zero data to display. Also fixed the seeder's rating-recompute step, which was passing a stringified property ID into a raw Mongoose aggregation `$match` — since aggregate pipelines aren't auto-cast, this silently zeroed out every property's rating on each reseed.
- Web owner workspace replaced its hardcoded placeholder numbers with real, server-scoped data — a new `GET /api/inquiries/received` endpoint plus the existing `GET /api/properties/mine` now drive a real "your listings + inquiries about them" view, verified against two different landlord/agency accounts to confirm correct per-owner scoping.
- Skeleton loading UI (pulse animation) on all card/list-shaped loading states on both web and mobile, replacing plain "Loading..." text.
- Backend/HTTP log timestamps now use Nairobi (`Africa/Nairobi`, UTC+3) time instead of UTC, including the app log file's day-rollover boundary.
- Dependency upgrades via Dependabot: frontend to React 19 + Vite 8 (resolving the `vite@5` dev-server CVEs) and mobile to Expo 57.0.2/React Native 0.86, `@react-native-async-storage/async-storage` 3.x, and other patch bumps — `eslint`/`jest` were deliberately held back on frontend/mobile because `eslint-plugin-react`/`eslint-config-expo`/`jest-expo` don't yet support `eslint@10`/`jest@30` (verified via a broken `npm ci`/crashing lint run before pinning back).

## Dashboard, Listing Management, and Testing Infrastructure

- Fixed a bug in the landing page's header "Sign in" button: the auth modal was nested inside the non-splash branch of a ternary, so it never rendered while the landing page itself was showing.
- Added Calibri as the primary body font (falls back to the existing Inter/system stack on platforms without it, since Calibri can't be legally bundled as a web font).
- Automated API testing: migrated `tests/app.test.js` from a homemade in-process request helper to [supertest](https://github.com/ladjs/supertest), and added a real-database end-to-end API flow test (`tests/integration/apiFlows.integration.test.js`) covering register/login, property CRUD, inquiries, viewing requests, reviews, and favorites — opt-in via `TEST_MONGODB_URI`, same as the existing MongoDB integration test. Building it surfaced three real bugs, now fixed: (1) `tests/helpers/nodeTestCompat.js`'s `after()` ran its callbacks after the *first* test in a suite instead of the last, masked until now because the only prior multi-`before`/`after` consumer had just one test; (2) `Review.updatePropertyRating` matched on a raw (non-auto-cast) aggregation `$match`, so `respondToReview`'s populated `review.property` (instead of a plain ObjectId) silently zeroed out a property's rating whenever an owner responded to a review; (3) `reviewController.js` never invalidated the `properties` response cache on review create/response, so a property's rating could appear stale for up to the cache TTL after a review was submitted.
- Built a Dashboard on both web and mobile that actually consumes the previously backend-only, role-aware `GET /api/dashboard/summary` endpoint — the User Stories documented what each role sees, but nothing in either app ever called it. Now it's the default landing view for every signed-in role right after sign-in (a new nav tab on web at `/dashboard`, a new first bottom tab on mobile), showing unread notifications plus role-specific sections. This is also the first landlord/agency/admin-facing screen on mobile, which previously had none.
- Fixed the web owner workspace's "Your listings" cards, which rendered as static, non-interactive `<article>`s with no click handler at all — landlords/agencies had no way to open or edit a listing once created, even though the backend's `PUT /api/properties/:id` had existed all along. Added an Edit action per card that opens a new `PropertyEditPage` (`/owner/properties/:id/edit`, gated by `canManageListings`) covering title/description/type/status, price, location, bedrooms/bathrooms/amenities, viewing type/instructions, and contact details; carries forward the existing `location.coordinates` on save since the update endpoint replaces the whole `location` subdocument and the edit form has no map picker to re-supply it.
- Added a "New listing" creation flow for landlords/agencies on both web and mobile, backed by the existing `POST /api/properties` endpoint (previously only reachable via seeding/direct API calls — neither app had any UI to create a listing at all). Web: a `PropertyCreatePage` sharing its form fields with `PropertyEditPage` via a new `PropertyForm` component, reached from a "New listing" button in the workspace header, gated by `canManageListings`. Mobile: a first-ever Workspace tab (role-gated: sign-in and landlord/agency/admin required, shown as a message otherwise) listing the signed-in owner's properties via the newly added `fetchMyProperties`, with a "New listing" header action opening a create form (`WorkspaceStack` → `PropertyCreateScreen`). Tenants retain read-only access everywhere (Discover/Saved/property detail) and cannot reach either creation path.

## Theming, Admin Role Correction, Feedback, and Username Login

- Consolidated the app's two-shade green palette (web's `--green`/`--green-dark` CSS variables, mobile's `colors.green`/`colors.greenDark`) down to a single dark shade everywhere, at the user's request. Previously `--green-dark` was deliberately re-lightened in dark mode (to `#4fbf7a`) to fix a text-contrast bug against the dark background (~1.4:1 contrast otherwise); collapsing to one literal color per the request reintroduces that low-contrast text in dark mode for elements that use the shared green (nav links, prices, stat numbers) — a known, explicitly-accepted tradeoff, not an oversight.
- Removed the web frontend's default-vs-Kenya-flag theme toggle, at the user's request — the Kenyan flag palette (previously the `data-theme="kenya"` variant) is now the only look, merged directly into `:root`. The separate light/dark mode toggle is untouched (mobile never had a theme toggle to begin with, only the one fixed palette).
- Replaced the web frontend's single cycling "Mode" button with an explicit two-option Light/Dark radio toggle (`role="radiogroup"`, native radio inputs under the hood) in the header's top-right corner, at the user's request. It's the same shared header on every page, including the landing page, and — unlike the old button — is no longer hidden on narrow phone widths.
- Corrected the admin role to match its user story: admins moderate users, not listings. Previously admins were quietly included in `listingManagers`/`propertyOwners`-style role checks across the property, inquiry, and viewing-request routes and controllers, plus the dashboard and user-summary "owner" sections — meaning an admin account could in principle create, edit, or delete any property, and view/manage inquiries and viewing requests, none of which matched the documented user stories. Removed admin from every listing-management role check on the backend (routes, `ensurePropertyOwner`/`ensureInquiryManager`/`ensurePropertyManager`, `listMyProperties`/`listReceivedInquiries`/`listPropertyInquiries`, dashboard and admin-user-summary "owner" blocks) and from the frontend/mobile's `canManageListings`/`listingManagerRoles` equivalents, and replaced the web `AdminPage` placeholder with a real user-management console (search/filter users, view a user's account summary and status history, change account status to active/suspended/banned with a reason) built on the admin API endpoints that already existed but had no UI.
- A general UI/UX audit pass across web and mobile: added missing error/success styling and Retry actions to pages and screens that previously only showed a dead end on failure (Saved/Workspace/Dashboard/Discover/Admin on web; Dashboard/Saved/Requests/Workspace/Discover/property-detail on mobile), fixed several 44px-minimum touch-target violations (mobile save/chip buttons), added `KeyboardAvoidingView` to the remaining mobile forms that lacked it, added a sign-out confirmation dialog on mobile, made the admin users table keyboard-accessible, replaced plain loading text with skeleton placeholders where it was still missing, shrunk an oversized 477KB logo asset down to 31KB for its actual 44×44 display size, and fixed a real bug where two mobile screens referenced an undefined `colors.green` (should have been `colors.greenDark`), making the primary "Create listing" button invisible.
- Platform feedback and testimonials: tenants, landlords, and agencies can submit general feedback about their experience; only admins can respond, and responding immediately publishes the feedback as a testimonial on the signed-out landing page. New `Feedback` model/controller/routes on the backend, a `Feedback` tab on both web (`/feedback`) and mobile (a 7th always-visible bottom tab), and a pending-feedback count added to the existing admin dashboard "platform moderation" panel. Building this surfaced a real caching bug: the admin-response endpoint wasn't invalidating the public feedback response cache, so a newly-published testimonial could take up to the cache TTL to actually appear.
- Username login: registration now also assigns every account an opaque, backend-generated username (e.g. `swiftcheetah284` — an adjective, a noun, and a number, never derived from the person's real name, specifically so it doesn't leak identity the way a name-based handle would), and login accepts either the account's email or this username. A one-off `backend/seeders/backfillUsernames.js` script assigns usernames to accounts that predate this feature. Verified against a real database: registered a new account, logged in with the generated username, with the email, and with a mixed-case version of the username (case-insensitive match), confirmed a wrong password still fails, and confirmed the backfill script only touches accounts actually missing a username.
- Small alignment fixes on the Discover radius/location filters: the web "Radius" control (a stacked label + select) was vertically floating against its shorter neighboring buttons because the shared `.header-actions` row centered items instead of aligning their bottoms; and the mobile "Near me" button didn't share the 44px touch-target height of the radius chips beside it, making it look shorter than its row.
- Follow-up to username login: users now choose their own username at registration (free text, no character restrictions) instead of receiving an auto-generated one. If the requested username is already taken, registration is rejected with a `409` and up to 3 available alternatives (the requested name plus different random-number suffixes) to pick from instead — both web and mobile show these as clickable/tappable suggestions under the username field. The opaque generator didn't go away: `backend/seeders/backfillUsernames.js` and the demo seeder still use it for accounts with no human to ask. Generalized the backend's `ApiError`/central error handler to carry structured extra data (like `suggestions`) through to the JSON response, and fixed both web and mobile's `apiFetch` helpers, which previously discarded every field but `message` from error responses.

## Notifications, Saved Searches, Scheduled Jobs, and Push Delivery

- Real notification inbox on web (`Notifications` tab, `/notifications`) and mobile (a `Notifications` bottom tab) — `GET /api/notifications`/`PUT /api/notifications/:id/read` existed already, but nothing in either app called them before this; notifications only ever showed up as a bare unread count on the Dashboard.
- Saved-search alerts: tenants can save a Discover location + radius search (`POST /api/saved-searches`, manage from the Account page/tab); publishing a new listing that matches a saved search now notifies its owner. The matching logic reuses the exact same filter-building/geo-radius code the property list endpoint already used for querying (extracted to `backend/utils/propertyFilters.js` to share it without a circular import between the property controller and the new matching service).
- Scheduled-jobs infrastructure (`backend/jobs/`, `backend/scripts/runScheduledJobs.js`, `npm run jobs`) plus four time-based notification sweeps, run every 15 minutes via a new Kubernetes `CronJob` (`k8s/backend-cronjob.yaml`) in production or manually elsewhere: nudging landlords/agencies about inquiries and viewing requests left unanswered for 48+ hours, reminding both sides of an approved viewing happening within 24 hours, prompting a tenant for a review once an approved viewing's date has passed (which also flips its status to `completed` — the enum value existed but nothing ever set it before), and nudging owners about listings live for 14+ days with zero inquiries. Deliberately standalone scripts (not an in-process timer) since the backend already runs multiple replicas behind an HPA — an in-process scheduler would fire once per replica and double-send every nudge.
- Push notifications on mobile via Expo's push service (`expo-notifications` + `expo-server-sdk`, not raw Firebase/FCM — the idiomatic zero-Firebase-project path for an Expo-managed app): registers/unregisters a device's push token around sign-in/sign-out, and the shared `createNotification` chokepoint now best-effort sends a push alongside every in-app notification, so every notification type above (and every one that already existed) gets push for free. In the process, found and removed a fully dead, never-wired-up predecessor: a `fcmTokens` array on the `User` model and a `POST /api/auth/fcm-token` endpoint that only ever wrote to that array and had no Firebase/sending code behind it at all.
- Seeded demo images for the 11 properties that had none, added an explicit "View details" link on mobile property cards (previously the only way in was tapping the whole card), and added one-tap call/email/WhatsApp contact actions to the property detail view on both web and mobile — a "Contact via {method}" button plus individually-tappable phone/email/WhatsApp lines, built from the owner's preferred contact method.
- Added a mobile light/dark mode toggle (`ThemeContext`, persisted via AsyncStorage) — mobile never had one before, only a single fixed palette. It's an icon-only sun/moon control in the top-right header of every screen (Login, Register, Dashboard, Discover, Saved, Workspace, Requests, Notifications, Feedback, Account), replacing the old inline "Dark mode" switch that only lived on the Account screen. Also redesigned the mobile Sign In screen with a branded gradient hero matching the landing page, hid the dev-only "Show API server settings" toggle behind `__DEV__` so production builds never expose it, and fixed the mobile landing page's gradient background not filling the screen on short content (now sized to the device's actual window height).
- Gated full property details (pricing, contact info, amenities) behind tenant sign-in on both platforms, using an existing-but-previously-unwired `canOpenPropertyDetails` helper — anonymous visitors and non-tenant roles now see a "sign in with a tenant account" prompt instead, while the Discover list itself stays public. Also removed the literal API base URL from the web frontend's footer tagline, so backend wiring is never shown to end users.

## Second Appraisal Round: Security, Race Conditions, and Data Integrity

- Ran a fresh appraisal round (backend/frontend/mobile/cross-cutting) and worked through its findings, phase by phase:
  - **Security & data hygiene**: the earlier ReDoS fix only covered `propertyFilters.js` — found and fixed two more `new RegExp`-from-raw-input call sites in `moverController.js`'s public mover search and `adminUserController.js`'s admin user search (`escapeRegExp` moved to a new shared `utils/regex.js` so it's not awkwardly imported from a property-domain module). Added CSRF protection (`middlewares/csrfProtection.js`): the httpOnly session cookie is `sameSite: "none"` in production (frontend/backend are cross-origin there), so it rides along on forged cross-site requests too — state-changing requests now require the `Authorization` header every real client already sends, closing the hole with no client-side changes. A follow-up self-review caught that the first pass only checked the access-token cookie, not the refresh cookie — `POST /api/auth/refresh` was equally forgeable via `keja_refresh` alone; fixed by trusting a body-supplied refresh token (unforgeable cross-site) instead of requiring a header refresh can never send. Also added `backend/uploads/` to `.gitignore` (locally-generated property images were untracked but one `git add -A` from being committed).
  - **Race conditions**: `DiscoverPage` (web) was the one data-fetching page without an active-flag guard on its fetches — a fast filter change could let an earlier, now-stale request overwrite a newer one. Refactored to the `appliedFilters` + single-`useEffect` pattern every other page already uses; auditing every other page's fetch effects for the same gap found and fixed two more real instances (`SavedPage`, one of `PropertyDetailPage`'s three effects). The identical bug existed in mobile's `DiscoverScreen.js` too (not originally flagged, found by applying the same scrutiny) and got the same fix. `MoversScreen`'s mover search got the missing active-flag guard plus a 300ms debounce on the county input (previously fired a request per keystroke). Found and fixed a real cross-user bug in `pushNotifications.js`: `registerForPushNotifications()` only sets its module-level token after several awaited steps, so a logout that started while an earlier login/session-restore's background registration was still in flight could see no token to unregister, then have that delayed registration land *after* logout and re-register the device under the now-signed-out session — fixed by having unregister always wait for any in-flight registration first. `NotificationsScreen` only ever loaded its list once, on mount; re-focusing the tab just silently marked everything read without ever refreshing the list, so a notification that arrived while the user was elsewhere got marked read before they ever saw it — now reloads on every focus, before marking as read.
  - **Data integrity**: `deleteProperty` only ever called `property.deleteOne()`, leaving uploaded image files (disk/S3) and every `Inquiry`/`ViewingRequest`/`Review`/`Favorite`/`PropertyImageFingerprint`/`MoverRequest` referencing it dangling. Now cascades to all of them, mirroring the thoroughness `deleteCurrentUser` already had for other entities — which, on closer inspection while building that mirror, turned out to have the identical image-file storage leak for the properties *it* deletes; fixed there too.

  Every fix above shipped with a regression test confirmed (via `git stash`) to fail against the pre-fix code and pass against the fix, plus live verification for the two changes hardest to trust from unit tests alone: a Playwright run against the real dev server proving the `DiscoverPage` race fix holds under an actual out-of-order network response, and a live run against the real backend/database proving `deleteProperty`'s cascade actually removes every dependent record. GitHub Actions has been fully unavailable throughout (account billing lock, unresolved since 2026-07-06 — not just failing runs, GitHub stopped queuing them entirely), so every one of these fixes relied on local test/lint runs instead of CI.
- Fixed `AUTHENTICATION_GUIDE.md`, which had gone stale describing auth state as living inline in `App.jsx` (true before the `AuthModal`/`AuthContext` extraction above, not since) and a hardcoded-array CORS example that never matched `backend/config/cors.js`'s actual env-driven, fail-closed-in-production logic. ## General Health-Check Appraisal: 28 Findings Across 6 Tiers

- Fixed a real crash-inducing gap the health-check appraisal found: `createSavedSearch` validated that `lat`/`lng` are provided together, but never that `radiusKm` requires them - so a saved search created with just `{radiusKm: 5}` passed validation, then made `buildPropertyFilters` throw, unguarded, inside `notifyMatchingSavedSearches` on *every subsequent property creation* (the property itself still saved, but the request errored). Fixed at the source (reject `radiusKm` without `lat`/`lng` at creation) and made matching itself resilient (`notifyMatchingSavedSearches` now skips and logs any malformed saved search instead of one bad document blocking every other saved search's match check). Verified live against the real running backend: the malformed payload is now rejected with a clear 400 instead of silently succeeding.
- Fixed a real privacy leak: `GET /api/properties` and `GET /api/properties/:id` are fully unauthenticated, yet populated every listing's `owner` with `"name email role phone verified"` - the owner's actual account email/phone, bypassing the dedicated `contact` sub-document (with its own `preferredMethod`) that exists specifically so an owner can choose *how* (or whether) to be contacted directly. Any anonymous caller could page through every listing and harvest owner emails/phones regardless of that preference. Split the projection: the two public endpoints now populate `"name role verified"` only; authenticated owner-facing endpoints (`listMyProperties`, `createProperty`, `updateProperty`, and the image-management actions - all gated on the caller managing their own listing) keep the fuller projection. Verified live against the real running backend: the public list/detail responses no longer include `email`/`phone`, while the authenticated owner's own view of the same property still does.
- Fixed stale property ratings surviving account deletion: `deleteCurrentUser` bulk-deletes a user's reviews via `Review.deleteMany(...)`, which never fires the `post("deleteOne")` hook that recalculates `Property.ratingAverage`/`ratingCount` - so a review left on *someone else's* still-existing property kept inflating/deflating that property's rating forever after the reviewer's account was gone. Fixed by capturing the distinct properties affected by the reviews about to be deleted (excluding the user's own properties, which are being deleted anyway) and explicitly recomputing each one's rating afterward via the existing `Review.updatePropertyRating` - reused, not reimplemented. Along the way, found and fixed a second gap in the same function: `deleteCurrentUser` never called `invalidateNamespace("properties")` at all, so a deleted property (or now, a just-recomputed rating) could keep serving stale cached data for up to the response-cache TTL. Verified live against the real running backend/database: created two reviews (5-star, 1-star) on a property, confirmed the average was 3.0/2, deleted the 1-star reviewer's account, and confirmed the property's rating immediately updated to 5.0/1.
- Fixed feedback being auto-published with no submitter consent: `respondToFeedback` unconditionally set `isPublic = true` the instant an admin replied to *any* feedback, with no opt-in anywhere - a user submitting a private complaint had no way to keep it private once an admin responded. Added an `allowPublicSharing` field (default `false`) to the `Feedback` model and creation schema, exposed as an explicit opt-in checkbox on both web (`FeedbackPage.jsx`) and mobile (`FeedbackScreen.js`, a `Pressable`-based checkbox rather than RN's `Switch` - avoids a real RNTL testing quirk where `Switch`'s `onValueChange` doesn't reliably fire via `fireEvent` in this test setup); `respondToFeedback` now sets `isPublic = feedback.allowPublicSharing` instead of unconditionally `true`. Verified live against the real running backend: submitted one feedback with consent and one without, had an admin respond to both, confirmed only the consented one appears in the public testimonials feed.
- Added state-machine validation on status transitions: `updateInquiry`, `updateViewingRequestStatus`, and `updateMoverRequestStatus` only ever checked actor authorization before applying a new status - an owner could "approve" a viewing request that was already `rejected`/`cancelled`/`completed`, re-triggering notifications and stomping timestamps on an already-terminal record, and the same shape of gap existed for inquiries and mover requests. Added a shared `assertValidTransition` helper (`backend/utils/statusTransitions.js`) plus a per-model `allowedFromByTarget` map (e.g. viewing requests: `approved`/`rejected` only from `pending`, `completed` only from `approved`) - reused across all three controllers rather than three separate ad hoc checks. Verified live against the real running backend: rejected a viewing request, confirmed attempting to then "approve" it now returns a clear 400 instead of silently succeeding; confirmed the legitimate `pending → approved → completed` path still works, and that `completed → approved` is correctly blocked too.
- Fixed "open"-type viewing requests (auto-approved, no fixed date - visit anytime) never getting review-prompted or auto-completed: `promptPostViewingReviews.js`'s job only ever queried on `requestedDate`, which open viewings never set (only `scheduled` viewings require/set it), so they silently sat at `approved` forever with the tenant never nudged for a review. ## Discover UX Polish and Performance Remediation Roadmap

- Collapsed Discover's filter bar (web) behind a "Filters" disclosure: Type/Bedrooms/Min rent/Max rent/Apply price used to sit always-visible in a 9-control flat row alongside Radius/Near me/Save search, presenting a first-time visitor with too many simultaneous decisions before seeing any results (a Hick's Law concern flagged during a frontend UX pass). Radius and Near me stay always-visible as the two lowest-effort, most-used controls; everything else now lives behind a "Filters" toggle button, which also reports the number of currently-active filters in its own label (e.g. "Filters (2)") so collapsing them doesn't hide that state from view. ## Security Audit: Backend Fixes (SSRF, NoSQL Injection, Info Disclosure)

- A full-codebase security appraisal (backend auth/authz, injection/validation, data exposure, frontend, mobile, and infra reviewed separately, findings independently verified against actual source before being trusted) surfaced 8 real findings. This PR closes the four backend ones that were self-contained, low-risk fixes; the rest (web/mobile token storage, docker-compose's exposed unauthenticated MongoDB port, and the mobile OAuth custom-scheme redirect once mobile Google Sign-In actually ships) are tracked separately as follow-up work.
- **SSRF via Web Push subscriptions** (`backend/controllers/pushSubscriptionController.js`): `registerPushSubscription` accepted an arbitrary `endpoint` URL with zero validation, and the server later makes a real outbound HTTP request to it (`webpush.sendNotification`) whenever any notification fires - trivially self-triggerable by the same attacker's own actions. Fixed by allowlisting known push-service hosts (`fcm.googleapis.com`, `updates.push.services.mozilla.com`, `notify.windows.com`, `web.push.apple.com`) and requiring `https:`.
- **NoSQL operator injection in property search** (`backend/utils/propertyFilters.js`): `type`/`listedBy`/`viewingType` were assigned straight from `req.query` with no validation, unlike the adjacent `status` field - `?type[$ne]=x` (Express's `qs` parser turns this into `{ $ne: "x" }`) reached `Property.find()` unmodified, confirmed to execute against a live MongoDB instance. Fixed by validating all three against their schema enums (newly exported from `Property.js` as `propertyTypes`/`propertyListedByOptions`/`propertyViewingTypes`, alongside the existing `propertyStatuses`), mirroring the `status` check exactly.
- **Unauthenticated health endpoints leaking DB internals** (`backend/controllers/healthController.js`): `/api/health`, `/api/health/ready`, and `/api/health/database` have no auth middleware, always included the live Mongo hostname/db name, and returned the raw driver error message verbatim on failure - a separate response path that bypassed the central error handler's production redaction entirely. Fixed with a `redactDatabaseHealth` helper that strips `host`/`name`/`path`, and a generic `"Database is not reachable"` message in place of the raw exception (the real message still reaches the server log via `logError`).
- **Unclassified 500s leaked raw exception messages in production** (`backend/middlewares/errorMiddleware.js`): only CastError/ValidationError/duplicate-key/Mongo-network errors got a rewritten, safe message - anything else (a library internal, a null-deref, an uncovered edge case) fell through with `err.message` unchanged. Fixed with a `messageIsSafe` flag (true whenever `err.statusCode` was explicitly set by application code, i.e. a deliberately-thrown `ApiError`, or one of the classified branches above fired) - only a message that isn't already known-safe gets replaced with a generic `"Internal server error"`, and only in production, so legitimate custom messages (e.g. `ApiError(503, "Google sign-in is not configured")`) are untouched.
- 498/498 backend tests passing (10 new, across 4 new/updated test files), lint clean.

## Security Audit: Session Revocation on Password Change

- Second fix from the same full-codebase security appraisal (see the SSRF/NoSQL-injection/info-disclosure PR for the first four). `PUT /api/auth/password` (`changePassword` in `backend/controllers/authController.js`) changed the password but never touched the `AuthSession` collection - the app already has a proper revocable refresh-token session model, used correctly on logout and account deletion, but this path missed it. An attacker holding a stolen refresh token (a leaked backup, a synced browser, a compromised device) kept full account access for up to `refreshTokenMaxAge` (30 days) even after the legitimate user changed their password specifically to lock them out.
- Fixed with `AuthSession.updateMany({ user, revokedAt: null, tokenHash: { $ne: currentTokenHash } }, { revokedAt: new Date() })` right after the password save - revokes every other outstanding session while excluding the caller's own current one (identified the same way `refreshAccessToken`/`logoutUser` already look it up, via `getRefreshTokenFromRequest`), so the device making the change isn't logged out mid-request. Falls back to revoking everything if the caller has no refresh token on hand at all.
- 2 new tests (revokes every other session while keeping the caller's own; revokes everything when there's no current refresh token to exclude). 487/487 backend tests passing, lint clean.

## Security Audit: docker-compose MongoDB No Longer Publicly Exposed

- Third fix from the same full-codebase security appraisal (see the SSRF/NoSQL-injection/info-disclosure and session-revocation PRs for the others). `docker-compose.yml`'s `mongo` service published port 27017 with `"27017:27017"` - no host IP prefix, so Docker binds it to `0.0.0.0` by default. The container has no auth enabled (no `MONGO_INITDB_ROOT_USERNAME`/`_PASSWORD`), so on any host running this file with a public IP and no external firewall, the entire database was reachable and writable by anyone on the internet with no login at all.
- Fixed by binding to loopback only (`"127.0.0.1:27017:27017"`) - the backend already reaches Mongo over the compose network (`mongodb://mongo:27017`) regardless of this mapping, which only exists so a local client (`mongosh`/Compass) can connect from the host machine. That local-dev convenience is preserved; remote reachability is closed.
- No code/test changes - config-only. Verified with `docker compose config` that the resolved port mapping now carries `host_ip: 127.0.0.1`.

## Security Audit: Web Auth Migrated to httpOnly Cookies + CSRF Tokens

- Last, and largest, fix from the same full-codebase security appraisal (see the other PRs above). The web frontend stored the auth JWT in `localStorage` and manually attached it as `Authorization: Bearer` on every request - any future XSS anywhere in the app would have been a full account-takeover primitive, since `localStorage` is plain JS-readable storage. The backend already issued an httpOnly session cookie alongside the token on every login/register/etc. response, but the frontend never relied on it.
- **The frontend now runs on cookie-only auth**: `frontend/app-utils/client.js` no longer has a `getAuthToken`/`setAuthToken` pair or a `keja_token` localStorage key at all - `apiFetch` already sent `credentials: "include"`, so the existing httpOnly `keja_token`/`keja_refresh` cookies now carry the whole session, with nothing about the token itself ever touching frontend JS.
- **This alone would have broken CSRF protection**, not just removed a redundant header: `backend/middlewares/csrfProtection.js` previously required every mutation (POST/PUT/PATCH/DELETE) to carry a real `Authorization: Bearer` header specifically *because* a cross-site forger could never read a token to put there - remove that header from the legitimate client too and the middleware would reject every mutation the app itself makes. Replaced it with a double-submit CSRF token: `sendAuthResponse` now also sets `keja_csrf`, a cookie deliberately **not** httpOnly (env-configurable via `CSRF_COOKIE_NAME`, default `keja_csrf`) alongside the session cookies. `client.js` reads its value and echoes it back as an `X-CSRF-Token` header on every mutation; `csrfProtection.js` now accepts either a valid `Authorization: Bearer` header (unchanged, still how mobile authenticates) *or* a matching `X-CSRF-Token` header + `keja_csrf` cookie pair - a forged cross-site request has the cookie ride along automatically same as before, but Same-Origin Policy means it can never read that cookie's value to also send it as a header, so the two can only match on a request the real frontend made itself. Cleared alongside the other two cookies on logout/account deletion.
- **`App.jsx`'s session-restore effect could no longer guess signed-in state from a stored token that doesn't exist anymore** - it previously skipped calling `fetchCurrentUser()` entirely unless a `keja_token` was already in `localStorage`. Since a returning user's actual session now lives in a cookie invisible to JS, the only correct way to know is to ask the server: the effect now always calls `fetchCurrentUser()` once on mount regardless, updating `signedIn`/`currentUser` from whatever it resolves to (a real session) or rejects with (none). Explicit sign-in/out (`handleAuthenticated`/`handleLogout`/`handleAccountDeleted`) still set state directly at their own call sites as before, so the effect's dependency array simplified to run once on mount rather than re-fire on every `signedIn` transition (a redundant re-fetch this file already had before this change, now removed as a natural side effect of the same rewrite). One accepted, unavoidable UX trade-off of this migration: a returning signed-in user briefly sees the signed-out UI on page load until the async check resolves, instead of the old (but no-longer-possible) instant optimistic guess.
- Testing: `backend/tests/middlewares/csrfProtection.test.js` gained 4 new cases for the header/cookie-pair path (matching pair passes; mismatched pair, cookie-with-no-header, and header-with-no-cookie all rejected); `authController.test.js` asserts the CSRF cookie is set non-httpOnly on register and cleared on account deletion. `frontend/tests/api-helpers.test.js`'s token-storage tests were replaced with CSRF-header-attachment tests (attached on mutations, absent on GETs); `frontend/tests/auth-flow.integration.test.js` (an opt-in, real-backend E2E test) gained a small manual cookie-jar shim, since Node's built-in `fetch` has no browser-style cookie store - it captures `Set-Cookie` from every response and replays it as `Cookie` on the next request, exposing only the non-httpOnly `keja_csrf` value via a `document.cookie` stub, matching exactly what a real browser would let frontend JS see. Also found and fixed a real, pre-existing test-isolation gap this change surfaced: two `app.render.test.jsx` describe blocks relied on `fetchCurrentUser` being left unconfigured to represent an anonymous visitor, but `vi.clearAllMocks()` (used throughout the file) clears call history, not a previously-set `mockResolvedValue` - meaning a signed-in mock configured by an earlier describe block in the same file could silently leak into a later one. ## Fix: CSRF Middleware Locking Users Out of Login/Register Itself

- **Real live bug, reported by a user hitting it in production**: signing in or registering on the web frontend intermittently failed with "This request must be authenticated with an Authorization header or a matching CSRF token" — the exact 403 `csrfProtection.js` throws for a *mutation on an authenticated session* it can't verify, except this was happening on the login/register request itself.
- **Root cause**: `csrfProtection` is mounted globally on `/api` (`app.js`), with no carve-out for `POST /api/auth/login`, `/register`, or `/google` — endpoints that *establish* a session, before any valid CSRF cookie/header pair can exist yet. If a browser carried any stale-but-unexpired auth or refresh cookie (left over from a previous or desynced session — plausible given frontend and backend sit on different Render origins in production, making every cookie here a third-party cookie subject to whatever a given browser's privacy mode does to those), the middleware saw an auth cookie present with no matching CSRF pair and 403'd the request — before it ever reached the login handler. With no way to recover: the one endpoint that reissues a fresh, matching CSRF cookie was the one being blocked.
- **Fix**: exempt `/api/auth/login`, `/register`, and `/google` from the CSRF check entirely, the same pattern `/api/auth/refresh` already used (a body-carried refresh token as proof instead of the cookie pair). These three take their own credentials — a password, or a verified Google ID token — as proof; a cross-site forgery of a login/register request gains an attacker nothing they don't already have, unlike a forged mutation replayed against an existing authenticated session, which is the actual threat this middleware defends against.
- Verified with new `csrfProtection.test.js` cases (all three exempted paths, stale mismatched cookies present) plus a live curl against the running dev backend confirming the request now reaches the login controller instead of being rejected by the middleware. Full backend suite (506 tests) and lint pass.

## Fix: CSRF Token Delivery for the Actual Cross-Origin Deployment

- **The previous fix wasn't the whole story**: the user kept hitting the same CSRF error on every action after signing in, not just login/register. The real, structural root cause: frontend and backend run on different Render origins in production (`kejaapp-frontend.onrender.com` vs `kejaapp-backend-7iu3.onrender.com`). Cookie storage is scoped by hostname — a cookie the backend sets via `Set-Cookie` is stored under the *backend's* origin. The browser still attaches it automatically to requests *to* that origin (that part isn't restricted), but frontend JS calling `document.cookie` on *its own* page can never see it — unrelated to `httpOnly`/`SameSite`, just how per-origin cookie storage works. `getCsrfToken()` in `client.js` read `document.cookie` specifically because the CSRF cookie is the one non-httpOnly cookie meant to be JS-readable — except in this split-origin deployment, it never actually was. Every mutation silently sent no `X-CSRF-Token` header, and `csrfProtection.js` correctly rejected all of them.
- **Why it slipped through testing**: the one integration test exercising the real HTTP flow (`auth-flow.integration.test.js`, gated behind `RUN_AUTH_E2E`) points its own "frontend" and "backend" at the same base URL — one origin — so its `document.cookie` stub could read the CSRF cookie fine there, without ever modeling the real cross-origin topology that's actually live.
- **Fix**: stop relying on `document.cookie` for this entirely. The backend now echoes the current CSRF value in the JSON body of `login`/`register`/`google`/`refresh` (`sendAuthResponse`) and `GET /api/auth/me` (`getCurrentUser`) — something the frontend's own `fetch` call can read regardless of which origin answered it, since that's reading its own response, not another origin's cookie jar. `client.js` holds this in memory instead, and `apiFetch` learns it automatically from any response that carries one, covering both a fresh login and restoring a session on reload via the existing session-restore call. The cookie itself is untouched and still what `csrfProtection.js` compares against; only where the client learns the value to echo back changed. `logoutUser`/`deleteCurrentAccount` clear the in-memory copy on success, mirroring the backend clearing its cookie.
- Also **strengthened, not just patched, the test that missed this**: `document.cookie` is now hardcoded to always read empty in that suite — proof the fix doesn't depend on cookie-readability at all; a regression back to reading `document.cookie` would fail every mutation in that suite loudly instead of silently passing.
- Verified: full backend (506 tests) and frontend (171 Vitest + 86 node:test) suites plus lint pass on both. Live end-to-end via a real Playwright browser against a real dev backend: logged in as a tenant, saved a property (a real mutation) and logged out (another mutation), both succeeding via the new mechanism. Honest limitation: local dev couldn't reproduce the *exact* original failure, since cookies are scoped by hostname, not port, so `localhost:5173`/`:5000` share a cookie jar — the diagnosis rests on standard, well-established cookie same-origin behavior for the real deployment, and the fix itself no longer depends on cookie-readability either way.

## Consolidate Web + API onto One Render Origin

- **Eliminates the cross-origin cookie problem at the source**, rather than just working around it: the previous two fixes made CSRF work correctly across two different Render origins, but any *future* cross-origin cookie assumption would be one careless change away from breaking the same way again. Asked how to remove the root cause; a shared custom domain was the first option discussed but is blocked on registering one (a real prerequisite, not something doable on the user's behalf), so the two Render services were merged into one instead — frontend and API are now genuinely same-origin.
- **`kejaapp-frontend` is retired, not renamed.** `backend/Dockerfile.render` (new, Render-only — the existing `backend/Dockerfile` used by `docker-compose`/Kubernetes/CI is untouched) is a three-stage build: build the frontend, build the backend's dependencies, then a final image that copies the frontend's `dist/` in as `./public` alongside the backend. `backend/app.js` serves it (`express.static` + an SPA fallback route for direct hits on client-side routes like `/discover`) whenever that directory exists, and falls back to today's plain JSON status message when it doesn't — so local dev, `docker-compose`, and Kubernetes (none of which ever have that directory) are completely unaffected. `render.yaml`'s build context widens to the repo root (`dockerContext: .`) to reach both `backend/` and `frontend/`, needing a new root-level `.dockerignore` (previously only per-directory ones existed).
- **`sameSite` decoupled from `secure`**: both were previously derived from one ternary (`authCookieSecure ? "none" : "lax"`), conflating "served over HTTPS" with "cross-site." A consolidated same-origin deployment wants `secure: true` (still HTTPS) *and* `sameSite: "lax"` (now same-site) together, which the old single derivation couldn't express. New `AUTH_COOKIE_SAME_SITE` env var, defaulting to the exact old derivation when unset — zero behavior change for `docker-compose`/Kubernetes, which stay genuinely cross-origin.
- **Two real bugs found only by actually building and running the consolidated image locally, not just reasoning about the architecture** — both would have broken production if shipped untested:
  - `CORS_ORIGIN` isn't actually dispensable just because it's same-origin now: Vite's build emits `crossorigin` on the module `<script>`/stylesheet `<link>` tags, which makes the browser send a real `Origin` header (CORS mode) for these requests despite being same-origin. Removing `CORS_ORIGIN` (the original plan) rejected every asset load with "Not allowed by CORS." Fixed by pointing it at the service's own URL instead of removing it.
  - Helmet's default Content-Security-Policy (`script-src 'self'`) silently blocks `frontend/index.html`'s static Google Identity Services `<script src="https://accounts.google.com/gsi/client">` tag - the frontend never had a CSP before, since it was a header-less static site. `app.js` now applies a loosened CSP (`script-src`/`connect-src`/`frame-src` extended for `accounts.google.com`) only when it detects it's actually serving the bundled frontend, so nothing else is affected.
- The just-shipped CSRF body-relay mechanism (previous two entries) is untouched — it's strictly more robust than cookie-reading and works fine same-origin too; reverting it to plain cookie-reading now that origins match would be pure regression risk for no benefit.
- Verified: full backend suite (508 tests, +2 for the new `authCookieSameSite` coverage) + lint. Built `backend/Dockerfile.render` locally and ran it end-to-end with a real Playwright browser: `/` serves the frontend (not the JSON status message), static assets serve with correct content types, a direct navigation to a client-side route (`/account`) works via the SPA fallback, `/api/health` still returns JSON, the baked `VITE_API_BASE_URL` value was confirmed present in the served JS bundle, and - after finding and fixing the CORS/CSP issues above - a real login, a real mutation (`POST /api/favorites`, 201), and cookie inspection all confirmed working with `Secure`+`SameSite=Lax` cookies genuinely visible to `document.cookie` same-origin, closing the loop on why this consolidation was worth doing.
- Docs: `docs/devops.md`, `docs/Deployment.md`, `README.md`, and `docs/live.md` updated to describe one Render service instead of two; the Kubernetes sections are explicitly called out as still, deliberately, two-origin - this consolidation doesn't apply there.

## Security Hardening: Widen .dockerignore's Secret-File Coverage

- **Found during a post-merge security review of the Render consolidation** (widening `dockerContext` to the repo root to reach `frontend/` alongside `backend/`): the accompanying root `.dockerignore` only excluded `**/.env`, `**/.env.local`, and `**/.env.*.local` — missing any other `.env.<name>` file that doesn't end in `.local`, e.g. the repo's own untracked `.env.notion` (holds a live Notion token).
- **Not currently exploitable, but worth closing anyway**: Render's actual build clones a fresh git checkout, where an untracked, gitignored file like `.env.notion` never exists at all, and no `COPY` instruction in `backend/Dockerfile.render` touches root-level loose files (only the `backend/` and `frontend/` subdirectories) — so nothing copies it into an image layer today. The exposure was narrow (only a manual, local `docker build .` run from a working tree with such a file present would include it in the build context sent to the Docker daemon), but a future edit adding a broader `COPY` could change that without anyone noticing the `.dockerignore` gap.
- **Fix**: broadened the three specific patterns to one general `**/.env*`, so any current or future dotenv-style secret file is excluded by default regardless of naming, rather than enumerating suffixes. Nothing in `Dockerfile.render`'s `COPY` steps reads any `.env*` file (including `.env.example` ones), so no re-include was needed.

## Fix: Multi-Tab CSRF Token Desync After the Render Consolidation

- **Real, live bug reported by a user right after the CSP image fix deployed**: "This request must be authenticated with an Authorization header or a matching CSRF token" while already signed in and doing something else — the exact error message from the original cross-origin CSRF bug (see the two entries above from earlier this session), but this time on the now-same-origin consolidated deployment, which made it initially confusing.
- **Root cause, confirmed by asking the user directly**: they'd had a tab open from earlier, then logged in or registered again (or reloaded) in a different tab since. The CSRF cookie is shared browser-wide per origin, but `client.js`'s in-memory `csrfToken` (needed since cross-origin `document.cookie` reads never worked — see the earlier fix) is per-page-load: a second login/register/reload rotates the shared cookie's value, and an older tab's stale in-memory copy no longer matches on its next mutation, even though that tab still shows itself as validly signed in (its auth cookie is untouched).
- **Fix, in two parts**: `csrfProtection.js`'s 403 now carries a machine-readable `code: "CSRF_MISMATCH"` alongside its existing message, rather than leaving the frontend to pattern-match on message text (fragile, and conflates "genuinely signed out" with "this tab's copy is just stale"). `client.js`'s `apiFetch` catches that specific code, re-fetches `GET /api/auth/me` to relearn the current token, and retries the original mutation exactly once — self-healing the desync automatically instead of surfacing the error and requiring a manual hard refresh. A 403 for any other reason (e.g. a genuine permission decision) is left alone, not retried.
- Verified: full backend suite (508 tests, `csrfProtection.test.js`'s existing rejection cases now also assert the new code) and frontend suite (171 Vitest + 87 node:test, 3 new cases covering the re-sync-and-retry path, the no-infinite-loop case when the resync itself yields nothing, and confirming a non-CSRF 403 is never retried) plus lint, both green.

## Database Backup + Restore Scripts, One Real Drill Performed (ISO 27001 5.30/8.13)

- **The last open item in the SoA's Phase 2 remediation roadmap, and the one it called "the single biggest gap by risk remaining on this list"**: no database backup-and-restore procedure existed at all. The original plan (enable MongoDB Atlas's built-in scheduled snapshots) turned out to be blocked - Atlas Cloud Backup only exists on M10+ dedicated clusters, not the free M0 shared tier this project actually runs on (`cluster0.<...>.mongodb.net`, Atlas's default free-cluster naming).
- **Built a self-hosted alternative instead**: `backend/scripts/backupDatabase.js` dumps every collection via the Mongo driver directly - not the `mongodump` binary, so no new system dependency to install anywhere this eventually runs - to a single gzip-compressed EJSON document (`bson`'s `EJSON.stringify(..., { relaxedMode: false })`, added as an explicit dependency; preserves `ObjectId`/`Date`/etc. exactly on round-trip, not just as plain strings) and uploads it via a new `backend/services/backupStorageService.js`. `backend/scripts/restoreDatabase.js` mirrors `cleanupTestData.js`'s existing dry-run-by-default/`--confirm`-to-act convention: prints the source backup key, the target Mongo host/db, and a per-collection document-count preview before doing anything, and only wipes/restores when explicitly confirmed.
- **A genuinely separate, private bucket - not the existing property-image one**: `S3_BUCKET` is public-read by design (property photos need to be publicly viewable). Reusing it for database dumps - which contain password/refresh-token hashes and PII - would have made backups publicly downloadable. New `BACKUP_S3_*` env vars (own bucket/credentials, same "empty = disabled" convention as `REDIS_URL`/`CLAMAV_HOST`/etc., except both scripts refuse to run rather than silently no-op, since they're always explicitly invoked by a human) point at a second, private Backblaze B2 bucket the account owner created for this.
- **One real restore drill, not just written and trusted**: seeded a scratch local MongoDB instance (a throwaway `mongod` on a non-default port, isolated from any real dev database) with known data, ran `npm run backup` against it - a real upload to the real private B2 bucket, confirmed present via the bucket's own list API - then dropped the entire scratch database to simulate real data loss, then `npm run restore -- --confirm`. Every document came back byte-for-byte identical, including `ObjectId`/`Date` type fidelity confirmed with `instanceof` checks in `mongosh`, not just a document-count or JSON-string comparison. The drill's scratch database and its backup object were both deleted afterward - only the scripts and documentation are left behind.

Three real automation paths were considered and deliberately deferred rather than half-wired: Render Cron Jobs (simplest, but not free - $1+/mo, no budget approved), a GitHub Actions `schedule:` workflow (free, but depends on the account's GitHub billing lock actually being cleared - last confirmed 2026-07-23, unconfirmed since), and a Kubernetes `CronJob` mirroring `backend-cronjob.yaml`'s existing pattern (works today with zero new infrastructure, but only matters once `k8s/` is an actually-deployed target). See `docs/devops.md`'s new "Backups and disaster recovery" section.
- **`docs/iso27001-statement-of-applicability.md`**: `5.30` and `8.13` upgraded from "N" to "P" in both places each is listed (§5 full assessment, §6 pending digest) - explicitly not "Y", since the automation gap is real. Phase 2 item 1 in the remediation roadmap marked partially done.

## Security Checklist Review: Account Lockout, Timing-Safe Login, Security Event Logging, and More

- **Checked the backend against a 15-item hardening checklist**, verifying each against actual code rather than assuming - most items already existed (HSTS via Helmet's default, session revocation on password change, CORS failing closed in production, `httpOnly`/`secure`/`sameSite` cookies, admin routes properly gated, no directory listing anywhere), a few items don't apply at all (no password-reset flow exists in this app to expire links or rate-limit; no AI/LLM integration exists anywhere to be prompt-injected), and one (restricting DB permissions) lives entirely outside this repo in MongoDB Atlas's dashboard. Five genuinely new findings, four fixed here:
- **Account lockout after repeated failed logins**: nothing existed at the account level before this - only the IP-based rate limiter on `/api/auth`, which resets on IP rotation and does nothing to stop a slow, patient, or distributed brute force against one specific account. `User.js` gained `failedLoginAttempts`/`lockedUntil` fields; `loginUser` increments on a wrong password, locks for a configurable window (`ACCOUNT_LOCK_DURATION_MINUTES`, default 15) after a configurable number of failures (`MAX_FAILED_LOGIN_ATTEMPTS`, default 5), and checks the lock *before* running the password comparison so a locked account doesn't get another free bcrypt-cost guess while locked. Resets on the next successful login.
- **Timing-based user enumeration, found while touching the same code**: `!user || !(await user.matchPassword(password))` looks identical for a missing identifier and a wrong password, but short-circuits *before* the deliberately-slow bcrypt comparison when the user doesn't exist - a nonexistent identifier responded measurably faster than a real one with a wrong password, leaking which identifiers are registered via response time despite the error message text being the same. Fixed with `compareAgainstDummyHash` (`utils/passwords.js`) - a fixed, precomputed bcrypt hash run through the same `bcrypt.compare` call when no real user exists, normalizing the cost regardless of outcome.
- **Security event logging**: failed logins, account lockouts, and CSRF rejections previously showed up nowhere but undifferentiated HTTP status codes in the generic Morgan access log - a failed-login 401 was indistinguishable from an expired-session 401 without reading request bodies. Added `logSecurityEvent` (`utils/logger.js`, routed through the existing `logWarn`/PII-masking pipeline) with a consistent `[SECURITY]` prefix, wired into `loginUser` (failed attempt / lockout / locked-account rejection) and `csrfProtection.js` (CSRF mismatch - noted as often benign given the documented stale-tab desync case, but still worth a record for anomaly detection).
- **Upload MIME-type verification now checks actual content, not just the claimed label**: `mimeType` was validated against a whitelist (`image/jpeg`/`image/png`/`image/webp`, SVG already correctly excluded), but only as a client-asserted string - nothing verified the decoded bytes actually matched. Added real magic-byte signature checks (JPEG's `FF D8 FF`, PNG's 8-byte signature, WebP's `RIFF....WEBP` fourcc) in `fileStorageService.js`'s `decodeImagePayload`, on top of the existing ClamAV malware scan.
- **Storage-time sanitization for free-text fields**, closing a defense-in-depth gap: nothing sanitizes user-submitted text before storing it - the app is currently safe only because nothing renders it unsafely (no `dangerouslySetInnerHTML` anywhere on web, React Native never interprets HTML on mobile), a render-time guarantee that's one future unsafe-render bug away from becoming stored XSS. Added `sanitizeText` (`utils/sanitizeText.js`, a simple non-ReDoS-prone tag-stripper, not a full HTML parser - the goal is "no markup survives," not malformed-HTML recovery) and wired it into the four highest-exposure free-text write points: property descriptions, review comments and owner responses, and feedback messages and admin responses.
- **Verified**: 578/578 tests passing (539 unit/opt-in-skipped + the 39-test real-database integration suite, run against a scratch local MongoDB), 0 lint errors. Every fix has a regression test - the account-lockout state machine (increment/lock/reject-while-locked/reset-on-success), the dummy-hash timing normalization (a real duration comparison, not just a return-value check), the magic-byte rejection, and HTML-stripping at two of the four wired write points.

## Fix: Google-Only Accounts Got a Raw Mongoose Error Instead of "Invalid Credentials"

- **A real production bug, reported directly by the account owner**: attempting a password sign-in against their own account (created via Google Sign-In, no password ever set) failed with a raw `Path \`password\` is required.` instead of the normal "Invalid credentials" message - a Mongoose `ValidationError` leaking straight through `errorMiddleware.js`'s deliberate (and correct, in general) pass-through of validation messages to the client.
- **Root cause, confirmed by reproducing it against the real schema (not the mocked tests)**: `User`'s `password` field is `required: () => !this.googleId` and both `password` and `googleId` are `select: false`. `loginUser` (`authController.js`) only ever selected `+password`, never `+googleId` - so on a failed-password attempt, the `user.save()` that increments `failedLoginAttempts` re-validates the whole document, sees `password` selected-but-empty (a real Google-only account) and `this.googleId` as `undefined` (simply never loaded, not actually absent from the database), and incorrectly concludes password is required after all. Verified precisely with a standalone Mongoose script against the real schema: reproduced the exact error message, then confirmed selecting `+googleId` alongside `+password` fixes it - Mongoose only skips required-validation for paths that are both unselected *and* unmodified, so partially selecting related fields is enough to trip this.
- **Fix**: `loginUser`'s query now selects `+password +googleId` together. Checked every other `User.save()` call site in the backend for the same class of bug (`confirmRole`, `updateCurrentUser`, `changePassword`, `updateUserStatus`, the Google-account-linking path in `googleAuth`) - none of the others are affected, either because they explicitly set the field that matters before saving (`googleAuth`'s linking case) or because they never select *or* modify `password`/`googleId` at all, which Mongoose correctly treats as "leave validation to whoever actually manages this field."
- **This does not give the affected account a password** - it was never supposed to have one. The fix only corrects the failure mode: a wrong password attempt on a Google-only account now correctly fails with "Invalid credentials" like any other wrong guess, instead of crashing with an internal validation message. Signing in on that account still means using "Sign in with Google."
- **New regression test**: `backend/tests/integration/loginGoogleOnlyAccount.integration.test.js` - a real-database integration test (skipped without `TEST_MONGODB_URI`, matching this suite's existing convention) creating a genuine Google-only `User` document and asserting `loginUser` returns a clean 401 rather than a 400 validation error. Confirmed it actually catches the regression by reverting the fix locally and watching it fail with the exact original message, then restoring it. The existing mock-based `loginUser` lockout tests couldn't have caught this class of bug at all, since they stub out `User.findOne`/`.save()` entirely rather than exercising real Mongoose validation.

## Fix: Sentry Crashed the App Under Expo Go, and a More Reliable Mobile Tunnel Setup

- **Resuming mobile dev via the tunnel path documented above surfaced a genuine regression: the app now crashed on launch instead of loading at all** - confirmed as `Fatal signal 11 (SIGSEGV), ... in tid ... (mqt_v_js)` via Android Studio's own Logcat (mobile testing had moved to a Windows-side Android Studio emulator this session, which made native crash logs directly visible with no adb pairing needed - a simpler diagnostic path than the physical-device tunnel work above). A large burst of "Could not find generated setter" warnings immediately preceding the crash looked alarming but turned out to be normal, harmless noise - Expo Go registers its whole built-in view-manager catalog at startup regardless of which of them a given project actually uses.
- **Root cause**: `App.js` unconditionally imports `@sentry/react-native` (added since the entries above, for backend/mobile error tracking). That package's `NativeRNSentry.js` calls `TurboModuleRegistry.getEnforcing('RNSentry')` as an *import-time* side effect - which throws immediately and crashes the whole app natively, before any JS error boundary can ever catch it, because Expo Go doesn't ship that native module at all. `mobile/src/services/pushNotifications.js` already solved this exact class of problem for `expo-notifications` (lazy `require()` behind an `ExecutionEnvironment.StoreClient` check, never a top-of-file `import`) - applied the identical pattern to Sentry: outside Expo Go, behavior is unchanged (Sentry still initializes and wraps the app); inside Expo Go, the package is never even `require()`'d, so the crashing native lookup never runs. Verified by extracting the actual served bundle afterward and confirming the compiled `require()` call stayed inside the ternary's false branch rather than being hoisted, then confirming a reload no longer crashed.
- **A second, unrelated crash cause found in the same session, on the same emulator**: even after the Sentry fix, the app still failed to load - Play Store's current Expo Go build had, once again, moved past this project's pinned SDK 57 (the exact pattern already documented above for a physical device, now recurring on an emulator too). Same fix: sideload the matching build from `expo/expo-go-releases` (`Expo-Go-57.0.9.apk`) - simpler on an emulator than a phone, just drag the APK onto the running emulator window in Android Studio.
- **The tunnel infrastructure itself got rebuilt more durably along the way.** Metro now runs as a `Restart=always` system service instead of a manually-launched process, so it survives crashes/reloads without babysitting - fed through a small local HTTP proxy that strips `multipart/mixed` out of the `Accept` header before forwarding to Metro. Root cause of needing that: Expo Go requests the JS bundle with multipart streaming (for its bundling-progress UI), and a free-tier ngrok tunnel reliably delivered every byte but never resolved the multipart terminator correctly on the client side - manifesting as the app hanging forever on "Bundling 99%..." with no error anywhere. Forcing Metro's plain, non-multipart response path fixed it outright. Separately, ngrok's free plan only grants one reserved domain, so the backend API (needed once the app got past the splash screen and tried to fetch real data) couldn't get its own tunnel alongside Metro's - solved with a second small router that path-splits one shared tunnel (`/api/*` to the backend, everything else to Metro), since the backend's own routes already live under `/api` and Metro's dev-server paths never do.
- **One more gotcha worth recording for next time**: `EXPO_PACKAGER_PROXY_URL` (the env var that makes Metro embed the tunnel's public hostname instead of its own local port in the manifest) **must be a real process environment variable, not one injected via `.env.local`** - Metro's own `UrlCreator.js` deliberately reads it from the "pre-dotenv" environment specifically to stop a project's `.env` file from being able to redirect connected clients to an attacker-controlled URL. A `.env.local` entry for it is silently ignored.
- **Verified**: manually reloading the app on the emulator after each fix - first confirming the Sentry crash was gone (clean Logcat, app reaches the dashboard), then confirming the SDK-mismatch fix separately. No new automated test for the Expo-Go guard itself (an environment-detection branch, not business logic) - the same reasoning `pushNotifications.js`'s existing, already-tested guard already established for this class of bug. `docs/dev/Troubleshooting.md`'s Expo/Mobile section expanded with the full recipe.

## Fix: Liquid Glass Tab Bar Crash - the Redundant babel.config.js Was Never Actually Removed

- **A genuine documentation error, found while finally being able to verify this on-device.** `Roadmap.md`'s Next section had recorded, since PR #254, that `mobile/babel.config.js` (which double-applies the Reanimated/worklets Babel plugin `babel-preset-expo` already auto-configures for SDK 57 - the leading theory for the Liquid Glass tab bar's crash-on-load) "has been deleted for real." It hadn't been: PR #254's actual merged commit touched 16 files (backend/frontend appraisal fixes, `mobile/package.json`'s `expo-dev-client` addition) but never modified `babel.config.js` at all - confirmed directly by diffing that exact commit against its parent. The file was still present and unchanged since the branch that introduced it (PR #253), three-plus weeks and several sessions later.
- **Confirmed the redundancy itself directly this time**, rather than continuing to trust the earlier theory: `babel-preset-expo`'s own source (`configs/expo.js`) auto-detects `react-native-worklets` being installed and adds `react-native-worklets/plugin` itself whenever it's not explicitly disabled - so the project's own `babel.config.js` re-declaring that same plugin applied it twice per file, a real Babel footgun for any plugin that installs a global transform.
- **Fix**: deleted `mobile/babel.config.js` for real this time. 38/38 mobile suites, 219/219 tests, 0 lint errors - confirmed unaffected by the removal, as expected (it's pure build tooling, not application code). Then actually verified live on an Android Studio emulator via Expo Go: the tab bar's spring animations that previously crashed the app now load and work correctly.
- **The lesson generalizes beyond this one file**: a PR title or a Roadmap bullet describing a fix is not the same as the fix landing in the actual merged diff - worth spot-checking the real commit when a "should be fixed" item resurfaces as still-broken, rather than assuming the historical record is accurate.

## Second Full-Codebase Security Audit: M-Pesa Callback Forgery Fixed, Everything Else Confirmed Clean

- **Follow-up to the earlier full-codebase security audit** (see that entry further up) - re-ran the same shape of review (one read-only agent each over `backend/`, `frontend/`, `mobile/`) to check whether anything shipped since then had reopened a gap or introduced a new one, rather than assuming the earlier pass's fixes were still holding.
- **Backend, frontend, and mobile all came back clean** against the categories that mattered most given this codebase's shape: NoSQL injection, IDOR/ownership checks across every resource controller, JWT/session handling, CSRF, path traversal, SSRF, command injection, crypto/token randomness, mass assignment, file-upload validation, `dangerouslySetInnerHTML`/DOM-injection sinks, token storage (mobile confirmed still `expo-secure-store`, never `AsyncStorage`; web confirmed still httpOnly cookies, never `localStorage`), deep-link handling, and Sentry PII scrubbing. Each agent explicitly reported "clean" rather than the review being cut short - the same bar the first audit held itself to.
- **One real finding, new since the first audit**: the M-Pesa STK callback (`POST /api/support-payments/callback`, `handleMpesaCallback` in `backend/controllers/supportPaymentController.js`) had no way to verify a callback actually came from Safaricom. The code's own comment claimed the lookup-by-`CheckoutRequestID` was sufficient because that ID was "Safaricom's own unguessable" value - but it isn't secret from the one party with a motive to forge it: `initiateSupportPayment` returns that exact `checkoutRequestId` directly to the paying user in its response. A signed-in user could initiate a real support payment, then POST a fake `{ResultCode: 0, MpesaReceiptNumber: "..."}` callback for their own `CheckoutRequestID` and mark it `completed` without ever actually paying. Impact today is a record-integrity gap on a voluntary donation feature, not a live financial or privilege exploit (Support KejaApp still isn't live in production - see Roadmap's Next section - and nothing currently reads `SupportPayment.status` to gate any feature, badge, or workflow) - but worth closing before either of those things changes.
- **Fix**: the callback route now carries a required secret path segment (`POST /api/support-payments/callback/:secret`), checked with a constant-time comparison (`crypto.timingSafeEqual`) against a new `MPESA_CALLBACK_SECRET` env var before anything else runs - a mismatch or missing secret acks Daraja's required `{ResultCode: 0, ResultDesc: "Accepted"}` shape (so Safaricom doesn't retry-storm a route it's not actually misconfigured against) but never looks up or touches a `SupportPayment` record. Unlike `CheckoutRequestID`, this value is never returned to any client - it only ever appears in `MPESA_CALLBACK_URL` (configured once, directly with Safaricom) and the server's own env. `MPESA_CALLBACK_SECRET` follows the same "required with teeth" pattern `STORAGE_DRIVER=s3`'s `S3_*` group already established: once the other four `MPESA_*` vars are set, `config/env.js` now throws at boot if this one is missing, rather than silently accepting unverifiable callbacks. `render.yaml`, `backend/.env.example`, `docs/dev/Payments.md`, and `backend/docs/openapi.js` all updated to match.
- **Verified**: new tests covering a wrong secret and a missing secret (both ack 200 without ever calling `SupportPayment.findOne`), plus every existing `handleMpesaCallback` test updated to send the correct secret; a new env-config test confirming the startup throw when `MPESA_CALLBACK_SECRET` is left unset alongside the other four vars. 588/588 backend tests passing (4 pre-existing, unrelated failures confirmed via `git stash` to already exist on `main` independent of this change - a Sentry-default-config test and a network-dependent backup-storage test, both environment artifacts of this sandbox, not regressions), 0 lint errors.

## Indemnity Policy and Director/Officer Indemnification Policy

- **New `docs/compliance/indemnity-policy.md`**, expanding the one-line indemnity clause already in `terms-of-service.md` §10 into a full standalone policy - the same pattern the Anti-Bribery Policy set. Grounded in actual Kenyan statute, not assumed from general knowledge: the **Law of Contract Act (Cap. 23) §3(1)**'s writing/signature requirement for a *guarantee*, and why that doesn't apply to this clause - it's legally an *indemnity* (a primary, independent promise), not a guarantee (a secondary promise to answer for someone else's debt), so a click-through Terms acceptance is legally sufficient for it. Also draws the actual limits from the **Consumer Protection Act, 2012**: §4(1) and §5(3) void any term stripping a consumer's right to a class proceeding or an implied warranty; §7 resolves any genuine ambiguity in the consumer's favor; §13/§15 make an "excessively one-sided" or "so adverse... as to be inequitable" term an outright prohibited unfair practice. The policy is explicit that it can't be read to waive any of these, or to cover KejaApp's own wrongdoing.
- **New `docs/compliance/director-officer-indemnification-policy.md`**, a distinct document covering the other direction - KejaApp indemnifying its own directors/officers, not users indemnifying KejaApp. Grounded in the **Companies Act, 2015** §§194-199: §194 voids any provision indemnifying a director against liability *to the company itself*; §195 confirms D&O insurance is separately permitted; §196 permits a "qualifying third party indemnity provision" (liability to an outside party) but voids it to the extent it covers a criminal fine, a regulatory penalty, or the costs of losing a criminal case or a case the company itself brought; §197/§198 require disclosure in the directors' report once such a provision exists. **Written honestly as forward-looking, not operative**: cross-checking `soc2-readiness-assessment.md`/`iso27001-statement-of-applicability.md` confirmed KejaApp isn't yet a registered company with directors in the Companies Act sense, so this document is preparation for incorporation, not a policy currently in effect - flagged plainly rather than glossed over, matching this project's existing "no board-level oversight yet" framing in `risk.md`'s organizational-risk item.
- Both fetched and read directly from the actual Acts (via `pdftotext` against the official PDFs) rather than relied on secondary summaries, the same verification standard the Anti-Bribery Policy set - one secondary source's claim about a Consumer Protection Act "§56 unconscionable conduct" section turned out not to match the extracted text at all (it's actually §13); caught and corrected before it ended up in the document.
- Cross-linked from `Governance-and-Policies.md`, `terms-of-service.md` §10, `code-of-ethics.md`'s frameworks paragraph, and `risk.md`'s organizational-risk item (repo + wiki). No code changes.
