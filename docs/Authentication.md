# Authentication

KejaApp uses JWT authentication with HTTP-only refresh-token cookies, fully integrated between the backend and both clients (web, mobile).

For the complete code walkthrough (frontend state shape, exact request/response JSON, token storage) see [AUTHENTICATION_GUIDE.md](https://github.com/Abdurleone/kejaapp/blob/main/AUTHENTICATION_GUIDE.md) in the repo. This page is the high-level summary.

## Registration

`POST /api/auth/register`

```json
{
  "name": "John Doe",
  "email": "john@example.com",
  "username": "johnkamau",
  "password": "SecurePassword123!",
  "phone": "+254712345678",
  "role": "tenant"
}
```

- `role` must be one of `tenant`, `landlord`, `agency` — admins can't self-register.
- `username` is **free text, chosen by the user** — no character restrictions, just non-blank after trimming. It is *not* generated by the backend.
- If the username is already taken, the API responds `409` with up to 3 available alternatives:

  ```json
  {
    "message": "Username is already taken",
    "suggestions": ["johnkamau284", "johnkamau1093", "johnkamau562"]
  }
  ```

  Both the web and mobile register forms render these as clickable/tappable chips that fill the field for you.
- Username is **immutable** after registration — there's no endpoint to change it.
- Accounts that existed before this feature was added are backfilled with an auto-generated opaque username (e.g. `swiftcheetah284` — an adjective, a noun, and a number, unrelated to the account's real name) by `backend/seeders/backfillUsernames.js`, since there's no user to ask.

## Login

`POST /api/auth/login`

```json
{
  "identifier": "johnkamau",
  "password": "SecurePassword123!"
}
```

`identifier` accepts **either** the account's email or its username (case-insensitive). Invalid credentials of either kind return the same generic `401` message, so a failed attempt never reveals whether the email/username existed.

## Tokens and sessions

- A short-lived **JWT** (`{ id, role }` payload) is returned in the response body and set as an HTTP-only cookie.
- A longer-lived **opaque refresh token** is also returned/cookied; only its hash is stored server-side (`AuthSession` model).
- `POST /api/auth/refresh` rotates the refresh token and issues a new JWT.
- `POST /api/auth/logout` revokes the current refresh session and clears both cookies.
- Web stores the JWT in `localStorage` and sends it as a Bearer token on every request; mobile stores it via the platform's secure storage through `mobile/src/api/client.js`.
- **CSRF protection**: the auth cookie is `sameSite: "none"` in production (frontend and backend are cross-origin there), so it's sent on cross-site requests too. State-changing requests (`POST`/`PUT`/`PATCH`/`DELETE`) therefore require the `Authorization` header — the cookie alone is rejected there (`backend/middlewares/csrfProtection.js`), and is only ever trusted for safe (`GET`) requests. `POST /api/auth/refresh` is the one exception: it trusts a refresh token supplied in the request body (unforgeable cross-site) since it never has an old access token to send as a header.

## Other auth endpoints

```text
GET  /api/auth/me         Current user (name, email, username, role, phone)
PUT  /api/auth/me         Update name/phone only — email, username, and role are ignored even if sent
PUT  /api/auth/password   Change password, requires the current password
```

## Error responses with structured data

`ApiError`'s constructor takes an optional third argument (`details`), which the central error handler spreads into the JSON response alongside `message`. This is how the username-conflict `suggestions` array gets to the client — and it's a general mechanism any future endpoint can reuse for structured error data, not something specific to usernames.

## Role-based authorization

- **tenant**: search, save, inquire, request viewings, review, submit feedback.
- **landlord / agency**: everything a tenant can do that doesn't require ownership, plus create/edit/delete their own listings, respond to inquiries/reviews on their properties, submit agency verification (agency only).
- **admin**: user account moderation only. Explicitly has **zero** listing-management capability — this is enforced on the backend (routes + controllers), not just hidden in the UI. Admins respond to platform feedback and agency verifications, and review violation records.

See [Admin User Management](Features-and-User-Stories#admin-user-management) for the full acceptance criteria.
